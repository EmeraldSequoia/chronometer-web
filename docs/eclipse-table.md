# Eclipse Table

`eclipse-table.html` is the primary, bookmarkable answer to "when is the next eclipse?" — a standalone page listing every solar and lunar eclipse from 15 years back to 15 years ahead (currently 2011–2041: 115 rows, 70 solar and 45 lunar), each with deep links that open the moment and place of maximum eclipse in the Observatory and the Chronometer, plus a per-eclipse EclipseWise "Details" link.

It is **not** part of the help system. The help pages, the index grid, and several face help fragments link *to* it, and none of them host the content — see [Entry points](#entry-points). The page is also the **single generator** of those deep links: no other page hardcodes an eclipse URL, and prose elsewhere names table rows instead.

Penumbral lunar eclipses are omitted throughout: the shading is barely perceptible by eye, and the app's own eclipse model is umbral-only, so their deep links would show "no eclipse".

## Anatomy of a Card

| Element | Content |
|---|---|
| Kind icon | One of six inline SVG symbols (see [Icons](#icons)) |
| Globe | Orthographic Blue Marble thumbnail centered on the maximum-eclipse point |
| Time line | UTC instant of maximum, then the same instant on the reader's clock |
| Description | Kind label + NASA's own visibility region (or path description) |
| Coordinates | The point the deep links jump to, labeled by what it means |
| Links | Observatory · Chronometer · Details (EclipseWise, new tab) |

Two misreadings drove the card's design (commit 5825002), and the layout exists to defeat them:

**The date is a UTC date.** Next week's eclipse is "Friday Aug 28" in UTC but starts Thursday evening across the Americas. So the time line pairs the canonical UTC instant with the same instant on the **reader's own clock**, zone always named:

```
2026 Aug 28  04:13 UTC · Thu, Aug 27, 9:13 PM PDT
```

The word "local" never appears: for a solar eclipse it is ambiguous, and the deep links open the apps in the *path's* time zone rather than the reader's. The weekday appears only on the reader's side (nobody should anchor to the UTC weekday), the year only when it differs from the UTC year, and the whole span is NBSP-joined so it wraps as one piece or not at all. `formatViewerDateTime` owns this rendering.

**The coordinates are not where you would watch from.** For a lunar eclipse especially, the maximum point is mid-ocean while the entire night hemisphere sees the event. The coordinates line therefore names what it is:

- `Moon overhead at 9.00°S 63.00°W` — lunar rows (the sublunar point)
- `Greatest at 65.22°N 25.24°W · 5:46 PM there` — solar rows, carrying the site's own wall clock, which is also the clock the deep-linked apps display

`formatSiteTime` renders the site time; it adds month and day when the site's calendar date differs from the UTC date (paths near the dateline), and returns null — dropping the site time rather than the card — if `Intl` rejects the zone.

## Data Pipeline

The dataset is a committed artifact, `src/help/eclipse-data.json`, generated by `scripts/scrape-eclipses.mjs` (run by hand every few years, **not** part of the build — `build.sh` only verifies the JSON exists). Sources are NASA GSFC's century catalogs, decade tables, Besselian-elements pages, and path pages, whose footers grant free reproduction with the acknowledgment "Eclipse Predictions by Fred Espenak, NASA's GSFC" (reproduced on the page).

| Field | Meaning |
|---|---|
| `tdMs` | TT (TDT) instant of greatest eclipse — the stored time |
| `nasaDeltaT` | NASA's per-row ΔT, kept for provenance |
| `kind` | `partial-solar`, `annular-solar`, `total-solar`, `hybrid-solar`, `partial-lunar`, `total-lunar` |
| `region` / `pathRegion` | NASA's visibility text; path description for central solar eclipses |
| `lat` / `lon` | Greatest-eclipse point (solar) or sublunar point (lunar) |
| `coordSource` | `besselian` (all 70 solar) or `catalog` (all 45 lunar) |
| `tz` | IANA zone at that point — 74 distinct, including 46 nautical `Etc/GMT±N` |
| `url` | EclipseWise page for the eclipse |

Two decisions in that data are load-bearing:

**Times are stored as TT, never UT.** NASA's published UT labels bake in frozen ΔT *predictions* of assorted vintages (the same 2024 eclipse carries 74.0 s on one page and 70.6 s on another, against the realized 69.184 s), and the archive never re-converts. The TT instant is what the geometry is computed in and is immune to all of it. UTC labels and deep-link times are derived at view time through the engine's own leap-exact ΔT (`convertETtoUT` in `astronomy/es-time.ts`), so the page and its links self-correct whenever the leap-second table is updated — no re-scrape, and the bundle rebuilds on every build.

**Solar positions are computed, not copied.** Each solar row's greatest-eclipse point is reduced from that eclipse's Besselian elements. The catalogs round to whole degrees — up to ~78 km, enough to miss a 21 km umbral path and draw a *partial* eclipse on a row labeled "total" — and the higher-precision path pages exist only for central eclipses. The reduction is validated against every path page (0.5′) and every printed circumstance block (0.25°). Lunar rows keep catalog coordinates, where the rounding is harmless.

See [`planning/2026-08-17-eclipse-precision-and-verification.md`](../planning/2026-08-17-eclipse-precision-and-verification.md) for the reduction and its validation.

## Deep Links

Both app links carry place, zone, and a frozen time; the apps merge them with stored settings:

| Link | Target | Extra params |
|---|---|---|
| Observatory | `observatory.html` | — (its eclipse simulator activates on arrival) |
| Chronometer | `selected.html` | `picks=bsvzsl` (Basel, Venezia, Selene), `body=sun\|moon` |

Every link sets `lat`, `lon`, `tz`, `t` (UTC ms of maximum, integer), and `dir=0` — frozen at maximum, so the visitor presses play to watch it unfold. Venezia shows the Sun for solar eclipses and the Moon for lunar ones via `body`.

Every value goes through `URLSearchParams`. This is not cosmetic: an unencoded `+` in a query string decodes to a space, which would turn the 26 `Etc/GMT+N` zones into invalid timezones that `Intl` rejects with a `RangeError`. The renderer suite asserts no raw `+` survives in any generated URL.

## Rendering

`src/eclipse-table-page.ts` builds the entire list client-side from the JSON embedded in the page, so the page works on `file://` with no fetch. Everything except the bootstrap line is exported pure logic, which is what lets the test suite exercise the real shipped renderer.

**Year groups.** One `<details>` per calendar year (UTC), each summary showing the year, the eclipse count, and a row of mini kind icons. The group containing the today marker and its two neighbors render open; the rest are collapsed. The open set is derived from the marker position rather than the calendar, so a late-December visitor sees next year's eclipses rather than a fully-past year.

**Today marker.** A banner between the last past and first future card, id `today`, with past cards dimmed. `armTodayRecenter` centers it at load, again at the `load` event, and on every `resize` — until the visitor's first wheel, pointerdown, or keydown, after which the page is theirs and is never yanked. The resize case matters because rotation, split view, and device-emulator size switches reflow every card into the ≤480 px layout while the browser keeps the old pixel offset, stranding the view above the marker. The scroll is plain synchronous `scrollIntoView`, deliberately **not** rAF-wrapped (embedded panes may never fire rAF), and is skipped entirely when the URL carries a hash or the navigation is a reload or back/forward — those defer to the browser's own scroll restoration.

**"Show all years"** expands every group, because Safari's find-in-page does not auto-expand collapsed `<details>` (Chrome and Firefox do), so Cmd-F for a year needs an escape hatch.

**Globes.** Each card's thumbnail is the location dialog's orthographic Blue Marble globe (`shared/mini-map.ts`), rendered at 96 px for a 48 px display and handed back as a PNG data URL. Rendering is lazy per year group (a closed group hydrates on first open) and strictly serialized through one shared scratch canvas — concurrent renders would capture each other's pixels, and 115 live canvases would be a real memory cost.

**Staleness nudge.** When today falls within about a year of the dataset's coverage end, a banner appears telling the reader to re-run the scraper.

**Text safety.** Region strings are third-party prose and are always set via `textContent`, never as markup; a test renders a hostile record to prove it.

### Icons

Six inline `<symbol>` definitions in the page shell, sharing the simulator's color language: `#f2e407` the Sun (Mauna Kea's `sunColor`), `#d96a1a` the eclipsed Moon (umbra hue from `earthShadow.png`, pushed toward orange), `#7e7e93` the sunlit Moon, flat `#4a6b96` the corona, and `#1e1e32` for the Moon silhouetted against the Sun. A `<use>` instance of a symbol must carry explicit `width`/`height`, or it inflates to the nearest viewport and shifts off its slot.

A **hybrid** solar eclipse is total along the middle of its path and annular only briefly at the ends. The point of greatest eclipse lies in the middle, so a hybrid row's links show a *total* eclipse — the page says so in prose. See [`planning/2026-08-19-hybrid-eclipse-note.md`](../planning/2026-08-19-hybrid-eclipse-note.md).

## Tests

`src/__tests__/eclipse-table-page.test.ts` (31 tests, jsdom) runs the real renderer and URL builders over the full committed dataset. It pins the epoch conversion against hardcoded values rather than the code's own mirror, asserts every row's deep link round-trips cleanly, pins the viewer- and site-time formats with explicit locale and zone so they hold on any machine, and covers the degradation paths (an `Intl`-rejected zone, a hostile region string, a marker with no future rows).

## Build Flow

`build.sh`:

1. bundles `src/eclipse-table-page.ts` with esbuild to `dist/eclipse-table-page.js`;
2. emits `src/eclipse-table.html` through `inject_partials`, which inlines the committed `src/help/eclipse-data.json` verbatim into the page's `<script type="application/json" id="eclipse-data">` block via the `{{ECLIPSE_DATA}}` token — a build guard refuses data containing `</script` or `<!--`;
3. copies `src/faces/thumb-eclipses.png` to the dist root, where it serves as both the index card's thumbnail and this page's favicon and apple-touch-icon.

To move the covered window forward, re-run the scraper (regeneration procedure in its header) and rebuild:

```bash
node scripts/scrape-eclipses.mjs --start 2016 --end 2046
```

## Entry Points

Everything links *to* the page; nothing embeds its content.

| Source | Links |
|---|---|
| `index.html` | The "Eclipse Table" face-card, third in the grid (`thumb-eclipses.png` — a center-crop of the Observatory simulator's totality photo, `src/shared/assets/totalEclipse.png`) |
| `help.html` | The standalone `.help-nav` entry (the nav is removed in embed mode), plus four in-body links from the "Understanding Eclipses" worked examples — Historical data, Watching a known eclipse (×2), and Discovering dates with no external knowledge |
| Face help fragments | Basel, Observatory, Selene, and Chandra each carry a one-sentence link with explicit `target="_blank"` — the face-page popover retargets only `http…` links (`help-popover.ts`), so a bare relative link would navigate the running app away |

In embed mode the help iframe's `<base target="_blank">` carries the in-body links out to a new tab.

The page itself has no `<base target="_blank">` (unlike `help.html`): it would hijack the internal `#today` and show-all anchors, so external links opt in per link.
